# A0.1 Phase 3 — SOL Realization 0.2 to typed MOOSE IR

Status: implementation candidate for issue #6.

## Accepted upstream boundary

This phase consumes the accepted SOL M0.8 exit baseline exactly as its semantic source:

- upstream: `HyungseonSong-plasma/simulation-ontology`
- merge: `bceaf4c66fb33202e097e54da429e51f652c234a`
- Public Contract: explicit `0.2` RealizationSpec boundary
- Adapter Protocol: explicit `0.2` realization-request boundary

Public Contract 0.1 and Adapter Protocol 0.1 retain their published meaning. Later SOL M0.10 / 0.3 result architecture is intentionally not consumed by A0.1.

## Authority split

```text
SOL authority                          MOOSE adapter authority
----------------------------------     -----------------------------------
RealizationSpec entity semantics   ->  MOOSE object selection
canonical relations/scopes         ->  local object names
canonical quantities + units       ->  supported exact-unit extraction
MappingPlan dependency identity    ->  later execution scheduling/effects
                                     local mesh/discretization policy
                                     deterministic .i serialization
```

MappingPlan action-id spelling is never interpreted as physics. The translator consumes the validated canonical RealizationSpec graph; action bindings establish plan/spec referential coverage but do not make strings such as `thermal.solve` semantic operators.

## First supported canonical slice

The translator deliberately supports only the published M0.8 steady 1-D thermal fixture.

| Canonical SOL 0.2 meaning | Adapter-local MOOSE realization |
|---|---|
| `ThermalTransport` | validated physics root; no native identity equivalence |
| `SteadyHeatEquation` | `HeatConduction` kernel |
| `FourierLaw` closed-by relation | required relation before kernel construction |
| `ThermalConductivity` + `thermal.conductivity` in `unit.watt_per_meter_kelvin` | `GenericConstantMaterial` scalar property `thermal_conductivity` |
| `Field` used by the BC relation | scalar Lagrange variable `T` |
| `LineDomain1D` + `geometry.length` in `unit.meter` | generated 1-D mesh on adapter-local chart `[0,L]` |
| `BoundaryPoint1D` at `0 m` | generated-mesh `left` boundary |
| `DirichletTemperatureBoundaryCondition` + `thermal.temperature` in `unit.kelvin` | `DirichletBC` on `T` |
| `StationaryAnalysis` | `Steady` executioner |
| `MaximumTemperature` observation intent | validated as supported request meaning; no canonical result is produced in Phase 3 |

Required canonical relations are checked explicitly: represented-by, closed-by, parameterized-by, defined-on, applied-to, and analyzed-by.

## Adapter-local policy

The following are deterministic backend choices, not SOL semantics:

- generated 1-D mesh uses `nx = 4`;
- the canonical line length is placed on a local `[0,L]` coordinate chart;
- MOOSE names `T`, `thermal_conduction`, `thermal_material`, `thermal_conductivity`, and `hot_wall_temperature` are local names;
- Exodus output is disabled in this Phase because canonical run/result semantics belong to later SOL 0.3 work.

A0.1 does not perform implicit unit conversion. The first slice accepts only the exact canonical units published by the fixture; another valid canonical unit is reported as unsupported rather than guessed.

## Distinguishability evidence

The SOL M0.8 fixtures intentionally keep the MappingPlan unchanged while changing RealizationSpec values:

- base: conductivity `45 W/(m K)`, hot-wall temperature `400 K`;
- alternate: conductivity `200 W/(m K)`, hot-wall temperature `500 K`.

Adapter tests require identical canonical MappingPlan identity, different canonical RealizationSpec identity, and different typed MOOSE IR / serialized `.i` values.

A separate counterexample renames every plan action and matching action binding while leaving the RealizationSpec physics graph unchanged. The serialized MOOSE input must remain byte-identical, proving that action-id spelling is not the mapping mechanism.

## Rejection policy

The phase rejects rather than invents meaning for:

- mixed Public Contract versions;
- missing RealizationSpec;
- hidden realization/physics fields in PlanAction extensions;
- unsupported target or capability set;
- missing/ambiguous required canonical entity types;
- missing required semantic relations/scopes;
- unsupported units;
- unsupported boundary positions or broader spatial graphs;
- non-positive domain length or thermal conductivity.

## Compatibility state

Two distinct compatibility statements are required:

1. **Translation consumption:** this Phase consumes exactly Public Contract 0.2 + Adapter Protocol 0.2 RealizationSpec semantics from M0.8 `bceaf4c...`.
2. **Runtime advertisement:** `FoundationAdapter::describe_adapter` remains on its established 0.1 operational surface with no declared target during Phase 3. Advertising operational Protocol 0.2 target/execution compatibility is deferred until Phase 4 actually wires and proves authoritative 0.2 execution.

This prevents translation-library support from being mistaken for end-to-end adapter protocol compatibility.
