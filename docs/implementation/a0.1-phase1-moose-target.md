# A0.1 Phase 1 — MOOSE Target Probe & Process Isolation

**Issue:** #4  
**Status:** implementation candidate

## Evidence target

Phase 1 tests one exact official Linux x86_64 pre-built MOOSE package:

```text
package = moose
version = 2026.08.12
build = mpich
subdir = linux-64
filename = moose-2026.08.12-mpich.conda
official channel SHA256 = d7b2eec6b958f11455c903b70a16ea319b7edb68b4499537313c06785abd05b3
```

Primary public references:

- MOOSE pre-built Conda installation guide: `https://mooseframework.inl.gov/getting_started/installation/moose_conda_binary.html`
- INL public Conda channel: `https://conda.software.inl.gov/public/linux-64/`
- MOOSE command-line usage: `https://mooseframework.inl.gov/application_usage/command_line_usage.html`

This is an exact backend evidence target, not a broad MOOSE version compatibility promise.

## Probe boundary

The backend probe records and validates:

- Conda package name/version/build and available metadata provenance;
- `moose-opt --version`;
- `moose-opt --show-type`;
- `moose-opt --show-copyable-inputs`, including `heat_transfer` availability;
- `moose-opt --help`, including advertised `--check-input` and `--json` interfaces;
- a `--check-input` invocation over a repository-owned backend-only generic diffusion fixture.

The backend-only input fixture is not canonical SOL thermal intent and is not a SOL-to-MOOSE mapping example.

## Process isolation

`MooseProcessRunner` launches the configured executable as a child process with:

- stdin disconnected;
- stdout and stderr piped and drained independently;
- bounded timeout;
- explicit child termination on timeout;
- exit status, timeout flag, stdout bytes, and stderr bytes returned as adapter-internal evidence.

No MOOSE console output is forwarded to the adapter JSON-RPC stdout channel.

## Workspace layout

Backend work uses a deterministic adapter-local layout:

```text
<root>/runs/<validated-run-key>/
  input.i
  stdout.log
  stderr.log
```

Run keys accept only ASCII alphanumeric characters plus `.`, `_`, and `-`. Backend paths are runtime/artifact facts, never canonical SOL identity.

## Capability discipline

Phase 1 intentionally keeps `AdapterDescription.targets` empty. An installed MOOSE package and the existence of `heat_transfer` inputs are backend facts; they do not by themselves prove a solver-neutral SOL mapping capability. Canonical target/capability declaration remains gated by accepted mapping semantics and conformance evidence.

## Evidence classification

Phase 1 may establish:

- exact backend package/executable evidence;
- process/log isolation;
- backend CLI/introspection availability;
- backend input parser acceptance for a backend-only fixture.

It does **not** establish:

- SOL-to-MOOSE thermal mapping correctness;
- Protocol conformance for a declared MOOSE target;
- successful thermal solve convergence;
- physical/numerical V&V;
- resolution of `simulation-ontology#110`.
