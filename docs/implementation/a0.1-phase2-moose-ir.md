# A0.1 Phase 2 — Typed MOOSE IR & Deterministic Input Serializer

**Issue:** #5  
**Status:** implementation candidate

## Purpose

Phase 2 introduces an adapter-local typed representation for backend MOOSE input construction. It is deliberately **not** a SOL Public Contract DTO, ontology layer, or solver-independent semantic representation.

The architectural seam is:

```text
future accepted canonical SOL realization payload
        |
        | Phase 3 translation (not implemented here)
        v
adapter-local MOOSE IR
        |
        v
deterministic .i serializer
        |
        v
exact-tested MOOSE executable
```

Phase 2 implements only the lower two layers.

## IR coverage

The typed IR contains enough backend structure for the planned first steady-conduction shape:

- generated one-dimensional mesh bounds and resolution;
- scalar finite-element variables;
- `Diffusion` or `HeatConduction` backend operators;
- constant material properties using `GenericConstantMaterial`;
- Dirichlet boundary conditions;
- steady execution;
- output enablement.

These type names describe adapter/MOOSE realization choices. They are not canonical SOL semantic classes.

## Determinism

Serialization validates the IR before output and applies stable ordering by adapter-local object name for:

- variables;
- operators;
- materials;
- boundary conditions.

The serializer also uses deterministic numeric rendering, explicit string quoting/escaping, and a fixed top-level MOOSE block order.

Golden regression tests verify byte-for-byte deterministic output for the backend-only diffusion fixture. Negative tests reject invalid identifiers, non-finite values, unknown variables, duplicate names/properties, invalid mesh bounds, and heat-conduction operators that reference an undeclared material property.

## Backend validation

Dedicated CI generates two backend-only inputs from the IR and submits them to the exact Phase 1 MOOSE target using `--check-input`:

1. generic scalar diffusion;
2. heat-conduction kernel plus a constant `thermal_conductivity` material property.

Passing these checks establishes only that the generated adapter-local artifacts are accepted by the tested MOOSE parser/configuration boundary.

It does not establish SOL mapping correctness, solve convergence, or physical/numerical V&V.

## Semantic gate

Phase 2 intentionally contains no conversion from `MappingPlanDto` or action IDs into MOOSE IR objects.

In particular, it must not infer physics from strings such as:

```text
thermal.material
thermal.solve
```

The upstream blocker `HyungseonSong-plasma/simulation-ontology#110` still governs the missing canonical solver-independent realization payload. Phase 3 remains blocked until that issue is resolved with an accepted versioned contract.

## Evidence boundary

Phase 2 may establish:

- typed backend realization structures;
- IR validation behavior;
- deterministic `.i` serialization;
- generated-input acceptance by the exact tested MOOSE executable.

It does not establish:

- canonical SOL-to-MOOSE thermal mapping;
- a declared solver-neutral MOOSE target/capability;
- Adapter Protocol conformance for thermal execution;
- physical/numerical correctness;
- broad MOOSE-version compatibility.
