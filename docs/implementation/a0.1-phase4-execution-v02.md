# A0.1 Phase 4 — Authoritative Protocol 0.2 MOOSE Execution

Status: implementation candidate for issue #7.

## Contract boundary

Phase 4 consumes the already-accepted Phase 3 mapping boundary:

```text
Adapter Protocol 0.2 ExecutePlanRequest
  -> Public Contract 0.2 RealizationSpec
  -> canonical thermal validation
  -> adapter-local typed MOOSE IR
  -> deterministic .i
  -> exact-tested MOOSE process
  -> Protocol 0.2 execution evidence
```

The semantic authority remains the accepted SOL M0.8 baseline `bceaf4c66fb33202e097e54da429e51f652c234a`. Phase 4 does not consume later SOL 0.3 result semantics.

## Compatibility advertisement

Following the M0.8 MOOSE handoff, `describe_adapter` advertises both frozen 0.1 and explicit realization 0.2 support:

```text
Adapter Protocol:  [0.1, 0.2]
Public Contract:   [0.1, 0.2]
target:            moose
capability:        thermal.steady_conduction
```

Protocol 0.1 validate/execute behavior remains non-realizing and rejects canonical MOOSE realization because 0.1 carries no `RealizationSpec`. Protocol 0.2 is dispatched through the dedicated realization runtime.

## Validate boundary

`validate_plan` remains advisory and side-effect free. For Protocol 0.2 it:

1. canonicalizes and re-parses the request;
2. verifies the exact `moose` target and narrow thermal capability;
3. invokes the Phase 3 canonical translator without executing MOOSE;
4. probes the current exact MOOSE package/executable state;
5. returns `accepted`, `rejected`, or `unavailable` using Protocol diagnostics.

No workspace or backend realization is created by validation.

## Authoritative execute boundary

`execute_plan` does not trust a prior validation response. It re-checks, in the current process/backend state:

1. Protocol/Public Contract 0.2 request coherence;
2. target and capability;
3. canonical RealizationSpec support;
4. deterministic typed MOOSE IR / `.i` construction;
5. exact MOOSE package identity and runtime probe.

Only after those pre-side-effect gates pass does execution create a unique workspace.

The backend sequence is:

```text
write input.i
  -> moose-opt -i input.i --check-input
  -> persist check.stdout.log / check.stderr.log
  -> moose-opt -i input.i
  -> persist stdout.log / stderr.log
```

The actual solve is invoked once. There is no automatic replay.

## Success evidence

A successful authoritative response:

- has `adapter_protocol_version = "0.2"`;
- reports every MappingPlan action exactly once;
- uses dependency-valid execution batches from the canonical plan topology;
- reports `completed` only after the exact MOOSE solve exits successfully;
- reports canonical `RealizationEffectDto` subjects, not MOOSE object names;
- has aggregate effects equal to the normalized union of action effects;
- keeps workspace/package/executable/input/log paths as opaque namespaced provenance.

For the narrow published thermal fixture, representative exact effects follow the SOL M0.8 reference response:

```text
thermal.domain   -> domain.main
thermal.material -> property.thermal_conductivity
thermal.solve    -> thermal.temperature_field
```

These associations are selected from each canonical action binding by supported subject semantics. The implementation does not interpret action-ID spelling as physics. `MaximumTemperature` observation intent is not reported as a result effect because canonical result semantics are outside A0.1.

## Failure and replay boundary

Before backend/workspace side effects:

- unsupported target/capability/realization semantics -> `rejected` response;
- temporarily missing backend runtime -> `unavailable` response;
- all action reports remain non-started or unavailable according to Protocol invariants.

After the execution boundary starts, a filesystem/process/check/solve failure is returned as an operational `ProtocolFailure` with:

```text
side_effects = may_have_occurred
```

This is deliberately conservative. A lost or failed authoritative execution response never creates retry or replay authority. Deterministic `.i` generation does not make `execute_plan` idempotent.

## Evidence boundary

Phase 4 establishes:

- explicit Protocol 0.2 runtime dispatch;
- authoritative current-state re-check;
- exact-target MOOSE invocation;
- deterministic workspace/artifact capture;
- dependency-valid action reports/effects;
- opaque backend provenance;
- conservative failure/replay handling.

Phase 4 does **not** establish:

- analytical or physical correctness;
- mesh/discretization adequacy;
- canonical result/observation semantics;
- broad MOOSE-version compatibility;
- performance/scalability.

Those are not inferred from Protocol conformance or backend process success.
